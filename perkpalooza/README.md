# Perk Palooza backend logic

This package contains domain logic only. The database models and migrations belong to the database-design branch and were not edited. The logic uses repository ports; a Django adapter is still needed to map these calls to the teammate schema.

## Schema alignment contract

- `accounts.User` uses email identity and the stored role values `giver`, `business`, and `admin`; the logic now uses those exact role values (`business` is the business operator role, `admin` is platform operations). The schema has no session/recovery-token models, so `AuthRepository` session and recovery persistence needs Django's configured session backend or another approved token store.
- `Card.serial_number` and `Card.code` are each unique and limited to 20 characters; the adapter must generate a serial number separate from the bearer code. `Card.code` is the bearer code in the current schema. `SecureCodeGenerator` generates 20-character codes and code lookup uses `get_card_by_code(code)`. The current model stores plaintext codes; at-rest hashing cannot be implemented without changing the schema. The code must never appear in logs or audit payloads.
- `Card.status` is `inactive`, `active`, `redeemed`, `expired`, `cancelled`, or `lost`. Payment state belongs to `Payment.status`; redemption must lock/recheck the active Card, create its OneToOne `Redemption`, and transition it directly to `redeemed` in one transaction. There is no persisted `redeeming`, `expired_locked`, or `lost_replaced` status.
- Card issuance must create/associate a prepaid `CardBatch` (one card, the selected `card_type`, `value_per_card`, and Payment relation) and then a `Card`. Map `delivery_method` to `card_type`, amount to `face_value`, `restriction_target_id` to exactly one of the business/category FKs, `replacement_for_id` to `replaces`, and create `CardDelivery`/`PhysicalShipment` rows for delivery. The schema has no Card or CardBatch `purpose` field; persist it in an approved external metadata store or request a schema change. NGN is the only supported currency and can remain implicit. Persist digital destinations in `CardDelivery` and shipping addresses in `PhysicalShipment`, not as extra Card fields. Map domain amount values to integer kobo for the schema's BigInteger money fields; Paystack receives/returns minor units at its adapter boundary.
- Payment maps to `Payment.paystack_reference`, `card_value`, `printing_fee_per_card`, `printing_fee`, `delivery_fee`, `platform_fee`, `paystack_fee`, and `total_charged`. Checkout persistence must populate every fee component and satisfy the model total constraint. Provider status maps to `pending`, `success`, or `failed`; cancellation is an application/audit outcome and maps to terminal `failed` in this schema. Fees are not wallet entries.
- Wallet entries use only the model choices `funded`, `committed`, `redeemed`, `released`, `refunded`, `locked`, and `reissued`. Their `available_change`, `committed_change`, and `locked_change` fields drive the projection. `WalletEntry` has no currency, reference, source/destination, or idempotency columns; NGN is implicit in the Wallet. Adapter-level row locking and checks against Payment/Card entries are needed to deduplicate because no unique entry key exists. `Wallet.available`, `committed`, and `locked` are cached projections, not the ledger source of truth.
- Float entries must use `deposit`, `redemption_draw`, `top_up`, `overdraft_cover`, or `adjustment`; the adapter must supply required `balance_after` from the locked ledger-derived balance.
- Business status values are `pending`, `active`, `paused`, and `removed`. Approval is derived from the separate vetting workflow; `active` means approved and live. A failed vetting decision remains a vetting record while the business stays `pending`, because there is no `rejected` status. `Business.user` is required and one-to-one, and `registration_number` is unique; onboarding logic therefore requires an already-provisioned operator user and registration number.
- `Category` has no approval field. The adapter should treat categories managed/curated by operations as eligible. `Business.low_float_threshold` is per business; it should be mapped from integer kobo to the domain's NGN amount. A zero threshold is treated as not configured and does not trigger automated alerts.
- `TopUpRequest` stores status and timestamps only. It cannot durably retain amount, reason, requester, or request key. A complete top-up request/review workflow requires those fields or a separate durable request store.
- There are no audit-log or outbox models in this schema. `record_audit` and `enqueue_outbox` require an external append-only audit/event store, or schema additions, before those guarantees are durable.
- `ValidationReport` has `code_entered` (max 50), optional Card, reason, status, and timestamps, but no operator or idempotency key. The logic stores a 48-character keyed fingerprint (not the raw code), which fits `code_entered`; request deduplication and authenticated actor attribution need an external audit store or schema support.
- `CardDelivery` and `PhysicalShipment` are the persistence targets for delivery/shipping. Card recipient/shipping metadata belongs in those rows where the schema places it, not extra Card columns. For the giver dashboard, the adapter must populate `Card.created_at` and the latest `CardDelivery.status` in the domain `Card` projection; those are not Card columns for delivery status.

## Dispute workflow logic

`DisputeService` supports giver disputes for owned cards, business disputes only for the business recorded on the card's Redemption, and platform-admin resolution. It maps to the existing `Dispute` fields/statuses (`open`/`resolved`) and emits audit/outbox events. Its repository adapter must lock the card row during duplicate-open checks. The business-side check reads the related Redemption because the Card model does not store a redeemed-business field.

## Required adapter guarantees

Implement `Repository` methods in a separate adapter module without changing models here. Use Django transactions and row locks for redemption and float updates. Build ledger changes from schema fields and kobo amounts, maintain `Wallet` cached totals from immutable WalletEntry rows, and use Payment/Card uniqueness plus locked state checks for replay safety. Never expose internal UUIDs as card codes. Keep notifications and delivery off the payment/redemption transaction; because the branch has no outbox model, use a durable external queue or add the model through the database owner.

The logic exposes `expire_due_cards()` as a bounded scheduled-worker entry point; the database adapter must select active/inactive rows with non-null expiry at or before the query time, and an application scheduler/management command still must invoke it.

## Delivery code encryption

`SecureCodeGenerator` and `FernetDeliveryCodeProtector` use the same dedicated Fernet key. Generate it with `Fernet.generate_key()` once, store it in deployment secret management, and pass it to both services as `encryption_key`; do not commit the key or derive it from Django's `SECRET_KEY`. The generator requires the key at construction so checkout cannot start with delivery encryption misconfigured. The ciphertext can be carried by an outbox payload without storing another database field.

## Remaining schema-dependent work

The business rules and ports can align to the current schema, but full persistence cannot be finished in this logic-only package. The following need the database owner or an approved external store: top-up request details/idempotency, durable audit/outbox, session/recovery-token persistence, raw-code-at-rest hashing, durable event and checkout idempotency, physical printing/delivery fee policy, nullable legacy card expiry handling, and the explicit approval/go-live distinction if operations needs both states. Local `config/settings.py` and `config/urls.py` also do not install the teammate's apps or expose these services as API routes. No database files were modified.
